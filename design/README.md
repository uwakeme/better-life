## 2. 方向：便签墙

参照物是冰箱上的便签墙、菜谱卡、手账贴纸。

| 轴 | 取值 |
| --- | --- |
| 明暗 | 浅（暖粉纸底 `#f2e8e3`） |
| 彩色策略 | 多色便签，8 色循环（柠檬 / 薄荷 / 桃 / 天蓝 / 紫丁香 / 米 / 麦 / 石板）；珊瑚色只留给警示条 |
| 字体 | 超粗黑标题（900 字重）+ 楷体批注 + 无衬线正文 |
| 形状语言 | 大圆角 18px + 硬偏移阴影（`4px 5px 0`） |
| 版式骨架 | 便签簇 + 贴纸，不是卡片列表 |

几个关键表达：

- **结论先行**：一张便签只说一件事，标题就是结论。
- **立场即贴纸**：推荐 ✓ / 避雷 ✕ / 中立 ?。颜色之外还有符号，不靠单一颜色通道区分。
  贴纸只贴在**要点**上 —— 立场是要点级字段（设计文档 §2.3），一条经验整体没有"推荐还是避雷"，
  所以经验卡只写「N 推荐 · M 避雷」这种诚实的计数。
- **领域即便签**：首页九个领域是九色便签簇，带序号和「N 张便签」计数。
- **要点即便签**：一条条可展开的便签，展开才给理由与适用条件。
- **依据是贴条**：依据来源页每条依据都写清它支撑哪几条要点，不是文末一串链接。
- **一面墙**：首页的经验流是**一份列表**，靠「最近更新 / 收藏最多」两个贴纸切排序。
  早先是「最近贴的」和「大家收藏的」两段，其实是一份数据的两种排法，分开列只是重复。
  「最近更新」按 `updated_at` 排 —— 设计文档 §3.1 / §3.2 首页写的就是「最近更新 + 热门」，
  数据库索引 `experiences (status, updated_at DESC)` 也是这个口径。
  墙上不再出现「复核」二字，原因见 §5 的口径调整说明。

## 5. 取舍与已否方向

### 为什么选便签墙

温度感最强，且「一张便签只说一件事」天然对上 §1.2 的「结论先行」。
领域是便签簇、要点是便签、立场是贴纸 —— 同一套隐喻贯穿三层，
用户不用切换心智模型就知道「结论」「理由」「出处」分别在哪。

### §2.5 口径调整：读者侧只留一个日期（2026-11-19）

设计文档原来写的是详情页固定展示「最后复核：YYYY-MM-DD · 内容可能随时间变化」，
数据模型里有 `reviewed_at`（必填）和 `next_review_at` 两个日期字段。原型评审时推翻了，理由三条：

1. **「复核」这个词不准**。内容全部由管理员自己录入、自己维护，没有第二双眼睛 ——
   它不是审核别人的稿子，是管理员回头确认「这条还成立」。叫「确认」才不误导。
2. **两个日期手工维护必然漂移**。演示数据里就有一个现成的例子：《快递丢了怎么赔》，
   管理员 2026-11-16 收到用户反馈「邮政局现在必须先在 APP 报案」，核实后改了第 1 条要点，
   而调整前 `reviewed_at` 还停在 2026-07-02 —— 内容改了、确认日期没刷新，
   页面就会对用户说「最后确认 2026-07-02」。**这比没有日期更危险。**
3. **「下次确认」是没人维护的承诺**。如果管理员其实不会定期回头看，
   这个日期只是又一条没人看的元数据。所以它只留在管理端当待办，不上读者界面。

落地结果：

| 位置 | 显示 |
| --- | --- |
| 首页 / 卡片 | 「更新 3 天前」 |
| 详情页 | 「更新于 2026-11-16」+「内容可能随时间变化」 |
| 管理·编辑页 | 更新于 / 最后确认 / 建议下次确认 / 可信度 |

设计文档 §2.5、§13、§17 已同步成这套口径：`reviewed_at` / `next_review_at` 降级为管理端字段，
读者侧展示 `updated_at`；演示数据里《快递丢了怎么赔》的三个日期也已按反馈处理时间对齐。

### §4.3 口径调整：三个并列按钮合并成一次提交（2026-11-19）

反馈盒每条反馈原来平铺着三个按钮：**回复 / 采纳 / 忽略**。评审时的问题是「这三个是不是重复了？
如果要点击的话应该怎么点？先点回复回复几句话，然后再点采纳或者忽略吗？」——答案是**不该这么点**，
因为三个按钮分属两条不同的轴，平铺在一条线上会让人去猜先后顺序：

- **结论轴**（这条反馈对内容有没有影响）：采纳 = 内容改了；不采纳 = 内容不改；
- **沟通轴**（要不要跟用户说话）：回一句。

「先回复再采纳」是一次提交该干两件事，不该拆成两步 —— 中间那一步如果忘了点，回复就发不出去；
如果先采纳再回复，用户可能先看到「已采纳」却收不到任何说明。所以改成：

**每条反馈只有一个「处理」主动作 → 面板里结论三选一 + 可选回复 → 一次提交**

| 面板里的选项 | 落库的 status | 含义 |
| --- | --- | --- |
| 采纳 | `accepted` | 内容按这条改了 |
| 不采纳 | `ignored` | 内容不改 |
| 只回话 | `replied` | 答复了，内容不用改（提问类反馈走这条） |

对应设计文档 §8.2 的 `PATCH /api/admin/feedbacks/:id`，body 就是 `{ status, reply }` ——
一次请求同时落状态和回复，天然不存在「只回了一半」。

原型里这个面板是真操作，不是摆设：没选结论就提交会被拦下并提示「先选一个怎么处理这条」，
选了「只回话」但不写内容会被拦下并提示「选了「只回话」，那就写点什么吧」；
提交后反馈的 status、reply、repliedAt 真的落进内存数据，卡片上的状态标签同步变成「已采纳」，
按钮也跟着改成「改结论」。演示数据里反馈 #2 是「采纳」（回复内容就是「已核实并更新第 1 条要点」），
反馈 #5 是「只回话」（提问类），待处理从 3 条降到 2 条。

### 管理员不提交反馈（2026-11-20）

内容全是管理员自己写的，他发现问题直接改就行 —— 绕一圈给自己提反馈没有意义，
提了还得自己回复自己。所以管理员视角下不出现任何提交反馈的入口：

| 位置 | 普通用户 | 管理员 |
| --- | --- | --- |
| 「我的」页 | 收藏夹 + 我的反馈 | **只有收藏夹** |
| 经验详情页 | 有「反馈」按钮 | **没有「反馈」按钮** |
| 「我的反馈」页 | 自己的反馈 + 「再写一条」 | 一句说明 + 指向「反馈盒」 |
| 「反馈提交」页 | 表单 | 一句说明 + 指向「经验编辑器」 |

注意区分两个东西：管理员**不提交**反馈，但**处理**反馈 —— 「收到反馈」指标和「反馈盒」入口照旧。
设计文档 §3.2 / §4.3 / §9.2 已同步。

### 文案口吻：界面说明用书面语，内容正文保持口语化（2026-11-21）

原型第一版的说明性文案偏口语（「该知道的事」「不会拿去做别的」「点一下看为什么」
「寄出反馈」「贴出去」），和产品要呈现的**可信经验库**形象对不上 ——
用户会把这种口吻理解成随手写的小工具，而不是一份有人维护、逐条标了来源的资料。
已把界面文案统一改成书面语：

| 位置 | 改前 | 改后 |
| --- | --- | --- |
| 「我的」页分组小标题 | 其他 / 该知道的事 | 其他 / 信息与说明 |
| 「我的」页隐私说明 | 这个库会记住你的微信标识……不会拿去做别的 | 本小程序会记录你的微信标识，用于登录与收藏，不会用于其他用途 |
| 「我的」页关于说明 | 内容全是管理员一条条写进来的 | 内容逐条录入，每条均标注来源（**同时去掉读者侧出现的「管理员」**） |
| 详情页免责行 | 身体不舒服先看医生，别照着经验库自己下结论 | 身体不适请及时就医，请勿仅依据本库自行判断 |
| 争议提示 | 有人说在某些情况下不适用……看的时候留意 | 有反馈指出其在部分情况下并不适用……请留意 |
| 反馈提交页 | 寄出反馈 / 这张便签哪儿不对？ | 提交反馈 / 这张便签哪里有问题？ |
| 我的反馈页 | 我寄出的 / 还没寄过反馈 | 我提交的 / 尚未提交反馈 |
| 编辑器按钮与草稿标题 | 贴出去 / 还没贴出去 | 发布 / 尚未发布 |
| 操作提示 | 点一下看为什么 / 点开看结论和依据 / 立场点一下就换 | 点击查看依据 / 点击查看结论与依据 / 点击切换立场 |
| 发布校验提示 | 还差 1 条依据，发出去之前得补上 | 至少需要 1 条依据，发布前请补充 |

**分界线**：**界面文案**（说明、提示、校验、操作引导）用书面语；
**经验正文**（管理员写的经验本体）保持口语化 —— 生活经验内容本来就该好读，
把它改成公文腔反而更难读。空状态（「墙上还空着」「盒子空了」）也保留便签墙的比喻语气，
那属于产品的视觉性格，不是口吻失控。设计文档 §13.4 同步了这条规则。

**防回退**：自检脚本 §⑦ 加了两组断言 —— ①读者侧页面不出现「管理员」；
②界面文案不出现那批口语词（用精确串匹配，不会误伤经验正文）。
之前这条口径只写在文档里、没有断言守着，「我的」页的关于说明就一直写着
「内容全是管理员一条条写进来的」，普通用户直接看得到。

### 为什么否掉另外两套（代码已删，理由留档）

**A · 对照台**（冷雾白 + 靛蓝 + 无衬线 + 大圆角卡片，签名元素是「推荐 / 避雷左右两栏对照」）

- 两栏对照在 375px 下每栏只有约 11 个字宽，长要点标题会折两行；
- 整体偏工具界面，温度不如便签墙。
- 它有一点值得记住：把立场做成左右两栏，是三套里最贴近 §1.2「好坏可分辨」的做法。
  以后如果想把调性换成「更专业」，可以按这个思路再出一版。

**B · 纸本**（暖米纸 + 衬线大标题 + 中文序号章节，搜索页是「检索单」，详情页是卷首引言 + 编号引用块）

- 刊头 / 第一期 / 卷首引言这套语汇把产品说成了一本**读物**，
  而 §1.2 要的是「掏手机就能搜到」、§1.3 又明确不做 UGC 与社区 —— 翻阅感会拖慢检索路径；
- 衬线大字占地方，一屏能装的信息更少。

### 删掉别名表，换成经验自带的「搜索关键词」（2026-11-23 追加）

管理端原来有一张**全局别名表**（洗头水 → 洗发水），用来做查询归一。核对后发现它不划算：

- 4 条别名里，2 条指向的「正式说法」在内容里根本不存在（`消费者投诉`、`市场监督管理总局` 都是 0 命中）；
- 1 条本来就是子串匹配（搜「硅油」已能命中「二甲基硅油」）；
- 真正有效的只有「洗头水 → 洗发水」这 1 条。

而它要养一张表、一个管理页、一组接口和一次归一化实现，维护责任还落在同一个管理员身上，很容易变成过期数据。

**改法**：`experiences.keywords` —— 每条经验写 0-3 个「别人可能怎么问」，写作时顺手填。
检索时并进匹配串，命中后如实显示「命中关键词：洗头水」；读者侧页面上看不到这个字段。
管理端少一页维护（「标签与别名」改叫「标签」），编辑器多一个可选输入框。

### 便签墙自己的代价

- 多色 + 硬阴影最容易显花，严肃场景（健康、钱财、维权）需要收敛配色；
- 楷体批注在安卓上大概率落不到 Kaiti，落地前要实测（见 §6）。
